# PPG-DaLiA: Heart-Rate Estimation and AI Agent

A notebook-based prototype for estimating heart rate from wrist PPG signals, comparing predictions with an ECG-derived reference, and explaining the results through a lightweight tool-calling AI agent.

The project explores two approaches: an interpretable frequency-based estimator and a small gradient-boosting model using PPG and wrist accelerometer features. It is an **experimental analysis, not a medical device or diagnostic tool**.

## Results at a glance

On the held-out **later portion of participant S1's recording** (917 overlapping 8-second windows):

| Method | MAE (BPM) | RMSE (BPM) |
| --- | ---: | ---: |
| Filtered PPG spectral baseline | 6.83 | 13.26 |
| Gradient boosting (PPG + accelerometer features) | **5.37** | **7.76** |

The learned model performed better overall, particularly during higher wrist-movement variability, but the spectral baseline was better on the lowest-movement group. These results cover **one participant's chronological test split**, not unseen participants or clinical use. See [REPORT.md](REPORT.md) for experiments, figures, unsuccessful attempts, and limitations.

## Dataset

Download **[PPG-DaLiA from the UCI Machine Learning Repository](https://archive.ics.uci.edu/dataset/495/ppg-dalia)** and extract its `PPG_FieldStudy` folder into `Data/`.

The notebooks expect files such as:

```text
Data/PPG_FieldStudy/S1/S1.pkl
Data/PPG_FieldStudy/S4/S4.pkl
```

The wrist PPG/BVP signal is sampled at **64 Hz**, and wrist acceleration (X, Y, Z) at **32 Hz**. ECG-derived reference heart-rate labels summarize **8-second windows, every 2 seconds**. The reference is used only as the training target and for evaluation—**never as a heart-rate prediction input**.

> **Data safety:** The supplied `.pkl` recordings use Python pickle serialization. Only load files from a source you trust; pickle loading can execute arbitrary code. Dataset files are intentionally excluded from the repository.

## Setup

Use a Python environment compatible with `requirements.txt`. From the project root:

```bash
python -m venv .venv
```

Activate it with `source .venv/bin/activate` on macOS/Linux or `.venv\Scripts\activate` on Windows, then install dependencies:

```bash
python -m pip install -r requirements.txt
jupyter lab
```

Open the notebooks in order. Their relative paths (such as `../Data/PPG_FieldStudy`) assume the notebooks are running from the `notebooks/` directory.

### 1. Explore the data

Run `notebooks/01_eda_visualization.ipynb`. Set `SUBJECTS` to the participants to explore (for example, `['S1', 'S4']`), then choose the displayed signal interval.

### 2. Estimate and evaluate heart rate

Run `notebooks/02_heart_rate_estimation.ipynb`. By default, the saved modeling run uses **S1**. `GRAPH_START` and `GRAPH_DURATION` select plotting intervals; model calculations use the recording's available windows. The notebook:

- Estimates heart rate using the dominant PPG frequency (Welch spectrum), with raw/filtered comparisons.
- Extracts PPG and accelerometer features and trains a histogram gradient-boosting regressor.
- Uses chronological **60% training / 20% validation / 20% testing** splits with gaps for overlapping windows.
- Chooses model/feature configurations on validation data, then reports held-out test metrics.

The last cell writes **`Data/test_predictions.csv`**, required for the agent. If you change subjects or rerun training, regenerate this CSV before running notebook 03.

### 3. Run the analysis agent

Run `notebooks/03_ai_agent.ipynb` **after notebook 02**. It reads the saved test predictions rather than retraining the model. Start with the deterministic tool, which requires no LLM:

```python
result = analyze_segment("S1", start_seconds=8000, duration_seconds=120)
print(result)
plot_segment("S1", start_seconds=8000, duration_seconds=120)
```

Only **complete windows in the held-out test period** are supported. The notebook displays the available subject/time range; a request outside it returns an error instead of inventing results.

**Optional local agent (Ollama):** Install [Ollama](https://ollama.com/), then download the tool-capable model used in the notebook:

```bash
ollama pull qwen3:4b
```

Ensure the Ollama service is running, then use:

```python
ask_agent("Analyze S1 from 8000 to 8120 seconds. What did you find, and what are the limitations?")
```

The agent asks the model to call `analyze_segment()`, executes that Python function, and sends its computed result back for an explanation. `plot_segment()` displays the same windows so the explanation can be checked visually. **MedGemma 4B was tested but could not be used for tool calling in Ollama** (`does not support tools`, HTTP 400); the submitted demonstration uses Qwen3 4B instead.

**Optional OpenAI agent:** `ask_openai(question)` is also implemented in notebook 03. It requires a valid API key in the notebook's local configuration and an API-enabled account. The notebook includes a placeholder only; the submitted outputs do not demonstrate a live OpenAI request. Ollama or the deterministic analysis tool is sufficient to reproduce the assignment without paid services.

## Design decisions and limitations

- **Interpretability first:** The spectral estimator provides a transparent baseline; the trained model tests whether PPG and movement features improve prediction.
- **Time-series evaluation:** No random window split; adjacent windows overlap heavily. The current chronological test evaluates later observations from S1, **not generalization to unseen people**.
- **Reference separation:** ECG-derived HR is not used to generate spectral or ML inference features. It supplies supervised training labels and evaluation comparisons.
- **Offline preprocessing:** Zero-phase filtering uses samples from both directions and is not a causal real-time pipeline.
- **Motion is not a diagnosis:** Accelerometer variability may indicate movement, but it cannot identify a specific action or prove the cause of any PPG artifact.
- **Grounded agent:** The agent must distinguish computed observations from possible explanations, acknowledge uncertainty, and avoid clinical claims. LLM wording should still be checked against the tool output.

Further investigation would include testing on unseen participants, checking performance per activity, and trying causal filtering. See [REPORT.md](REPORT.md) for the full discussion and resources used.
